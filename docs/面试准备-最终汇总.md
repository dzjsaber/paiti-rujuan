## 0. 面试前必须记准的事实

### 当前真实状态

- Android 客户端：React Native + Expo SDK 57 + TypeScript strict。
- 本地数据：Expo SQLite，FTS5 trigram 检索，版本化迁移 v1-v9。
- AI：智谱、DeepSeek、自定义 OpenAI 兼容接口；用户自备 API Key。
- 可选后端：FastAPI + SQLAlchemy + SQLite，邮箱验证码登录、JWT、云备份上传/恢复。
- Agent 化讲解：已实现并在 Expo Go 真机验收，使用智谱时错题工具成功触发；
  未绑定教材和自定义接口回退也通过。
- Agent trace：记录每轮模型耗时、usage、工具参数长度、工具耗时和结果长度。
- Agent Skills：`quick_explain`、`grounded_explain`、`wrongbook_review` 三种场景路由，按场景限制工具子集。
- 评测脚本：30 个固定案例已准备好，默认只校验夹具，设置 `ZHIPU_API_KEY` 后可跑真实模型评测。
- 客户端测试：8 套 126 项离线用例。
- 后端测试：17 项 pytest。
- APK：EAS 构建完成，约 99.9MB；构建提交 `679ac08`，记录提交 `bfa1634`。
- 云端备份本地服务：邮箱登录、上传、下载链路已验证；空设备完整恢复和最终 APK 内未完整实测。
- 公网部署：未做。当前是局域网自托管；电脑关机后云备份不可用。

### 绝不能夸大

- 不说用户量、DAU、留存、生产并发和准确率百分比，因为没有真实规模数据。
- 不说“公网已上线”“高可用”“自动扩缩容”，因为只做了本地和 EAS APK。
- 不说“Agent 完全流式输出”。工具轮是非流式；过程状态实时显示，最终正文在检索完成后出现，
  达到轮数上限时最后一次总结走流式。
- 不说“云端数据端到端加密”。SQLite 中是明文 JSON，服务端管理员理论上可读。
- 不说“任何 OpenAI 兼容接口都支持 Agent”。自定义接口目前回退为单轮讲解。
- DeepSeek 的 function calling 已按标准协议实现，但没有像智谱一样单独做完整真机验收。

## 1. 简历与项目介绍

### 简历条目（可直接改用）

> 独立开发 Android 刷题应用：React Native + Expo + TypeScript strict，完成拍照/文档 →
> AI 结构化提取 → 确定性校验 → 人工确认 → SQLite 题库 → 刷题/错题/教材 RAG → Agent 讲解闭环；
> 实现 8 套 126 项客户端离线测试和 17 项后端测试；另建 FastAPI 可选云备份服务，
> 支持邮箱验证码、JWT、限流、用户隔离与 20MB 备份限制，已通过 EAS 构建 APK。

不要写“已上线 SaaS”或“高并发服务”。可以写“自托管可选云备份服务”。

### 30 秒介绍

个人备考时，题目散落在照片、PDF 和课件里。我把它做成“拍题/导入 → AI 提取 → 确定性与人工
校验 → 本地题库 → 刷题和错题 → 教材引用讲解”的完整闭环。移动端离线优先，云备份是可选项；
讲解用 RAG，后来升级为最多 3 轮的轻量 Agent，让模型自主查教材、题库相似题和历史错题。

### 2 分钟介绍

在 30 秒版上补充三点：

1. 数据以 SQLite 为唯一事实源，FTS5 trigram 做本地教材检索，迁移版本化、恢复单事务。
2. AI 输出先过 Parser 和 10 类 F2 确定性校验，再进入人工确认，避免概率输出直接污染题库。
3. 后端只做认证和最新一份 JSON 备份，不解析题库；恢复按稳定 ID 合并，不覆盖本机已有数据。

### 为什么做这个项目

解决“散落试卷变成可刷题库”的沉淀问题，而不是做拍照直接搜答案。项目同时覆盖移动端、
本地数据、LLM 协议、检索、后端认证、测试和发布，是完整的个人全栈实践。

### 和搜题产品的区别

定位是个人题库管理，不做社区和搜答案；AI 只是候选生产者，入库必须经过确定性校验与人工确认；
数据默认本地，云备份需要用户主动开启。

## 2. 架构与关键选型

### Q1：整体架构怎么分层？

- `core`：领域模型、F2 校验、检索词、Agent 循环等纯逻辑。
- `db`：SQLite schema、仓库层、FTS、备份恢复。
- `services`：LLM、文档解析、图像、云 API。
- `screens`：状态和界面。
- `server`：FastAPI、SQLAlchemy、验证码/JWT、备份存取。

分层的价值是：纯逻辑能离线测试；SQL 能用 `node:sqlite` 跑真实迁移；UI 变化不会污染模型协议。

### Q2：为什么选 React Native + Expo？

单人开发、单端 Android；Expo 官方模块覆盖相机、相册、文件、SQLite、SecureStore 和分享，
EAS 可直接出 APK。代价是原生能力受 Expo Go 限制，部分 Node 库与 Hermes 不兼容，
新增原生依赖后需要重启 Metro，复杂导航后期可能需要迁移成熟路由库。

### Q3：为什么用 SQLite + FTS5，不用向量库？

个人题库和教材规模小，FTS5 零额外服务、随应用分发。检索用 3 字滑窗 OR + bm25，
短于 3 字回退参数化 LIKE。向量检索需要模型和额外存储，对当前数据规模收益不足。
承认 FTS5 是词面检索，不是语义检索。

### Q4：为什么导航是自研状态机？

页面少、依赖少，联合类型加 props 足够。局限是无深链、无导航栈缓存、返回逻辑手写；
页面继续增长应迁移 React Navigation 或 Expo Router。面试时把它说成阶段性取舍，不是优点包装。

### Q5：为什么多 LLM 提供商要抽象？

统一为 OpenAI 兼容协议，`complete` / `completeStream` 接收模型、端点、Key。
提供商差异用能力开关处理：智谱支持 `web_search`；智谱/DeepSeek 支持 thinking；
DeepSeek 图片需要 data URI；自定义客服端不支持工具时回退单轮。

### Q6：一条识别数据流是什么？

拍照/相册 → 压缩（长边 2000、JPEG）→ Base64 → RecognitionEngine → LLMService →
ResponseParser → F2 确定性校验 → 草稿持久化 → 人工确认 → 单题事务入库 → 刷题。

文档路径是：本地提取 TXT/MD/DOCX/PDF/PPT/PPTX → 分块 → 云端结构化切题 → 答案表映射 →
同一确认页。

## 3. 模型输出、校验与可靠性

### Q7：模型输出不可靠怎么办？

三层防线：

1. `ResponseParser`：严格 JSON → 去 Markdown 围栏 → 平衡扫描提取顶层数组；只做有限修复，
   如裸换行、未转义 LaTeX 反斜杠。
2. F2 确定性校验：结构、题型、选项完整性、题干、页内去重、置信度、视觉特征、答案缺失、
   来源和错误可见。
3. 人工确认：绿/黄/红标，红标不可直接入库。

### Q8：确定性校验具体拦什么？

单选/多选/判断/填空的答案类型一致性；选项至少两项、id 唯一、文本非空；题干有效性；
页内重复；来源可追溯；答案缺失进入 pending；无效字段必须可见。模型给的 confidence
只能作风险提示，不能作为可信结论。

### Q9：遇到过模型幻觉吗？

有。免费视觉模型曾漏掉原卷一道轴对称题，又虚构了一道原卷不存在的题；人工对照原图才发现。
这说明 Parser/F2 能拦截结构和枚举错误，但拦不住语义幻觉，所以必须保留原图核对和人工确认。

### Q10：模型怎么选型？

用固定样本做同卷对照，而不是凭价格推断。曾实测免费视觉档、付费视觉档和 DeepSeek：
免费档速度波动大；付费思考模式可能更慢；DeepSeek 关思考后速度和成本更适合识别。
结论是按任务分别选模型，并保留降级和超时/取消。

### Q11：模型自评 confidence 可信吗？

不完全可信。项目曾出现一批草稿 confidence 全为 0 的情况。策略是缺失或 0 进入人工复核，
最终入库由确定性规则和人工判断决定，不使用模型自评分替代校验。

### Q12：图形题怎么处理？

模型输出图形 bbox 后，本地裁出题干图/选项图；坐标体系做兼容和 clamp，确认页支持重截和移除。
模型坐标不稳时，用户手动框选兜底。自动配图被定位为草稿能力，不宣称永远准确。

### Q13：漏题怎么兜底？

整页识别失败或 0 题时，本地切上下半页再识别合并；确认页支持框选补识别；答案文档映射后
检查题号缺口；最差人工补录。拍摄倾斜和模糊是主要变量。

### Q14：文档导入踩过什么坑？

- PDF 用兼容 Hermes 的 pdfjs-dist 3.x。
- DOCX 用 mammoth；PPTX 解 OOXML；老 `.ppt` 自研 CFB + PowerPoint 记录流解析。
- 文档分块 3000 字符，优先题目边界，保留重叠和字符区间。
- 政治类内容可能被智谱内容审核拒绝，因此切题提供商可切换。
- 取消若只设标记会等当前块完成，后来加入 AbortSignal 立即中断且不重试。
- 答案表冲突不猜，显式标记复核。

### Q15：手势交互踩过什么坑？

最初手写 PanResponder，Android 第二根手指加入时事件链不稳定。后来迁移到
`react-native-gesture-handler`，并改为框选/缩放互斥模式。关键坑是 RN Modal 是独立原生视图树，
Modal 内必须再包 `GestureHandlerRootView`，否则框选和缩放全部失灵。

## 4. 教材 RAG 与 Agent

### Q16：RAG 怎么实现？

教材切成约 500-800 字片段，写入 FTS5 trigram；题目文本清理标点后取 3 字滑窗，用 OR 查询、
bm25 排序取 TopN；命中的片段进入 prompt，要求只依据教材并标注 `[编号]`。
证据为空时返回固定句，经用户确认后才能联网或使用模型知识。

### Q17：教材命中率怎么从 2/8 修到 8/8？

现象是“教材明明有，模型说没覆盖”。用真实 8051 课件和 8 道可确认题目复现，发现旧实现把
题干截断后当连续短语匹配，措辞或标点稍变就 0 命中。改为 3 字滑窗 OR 查询、bm25，
并修复长片段截断导致答案落在可见窗口外的问题，最终 8/8 命中且包含正确段落。

### Q18：为什么从 RAG 升级到 Agent？

RAG 是“固定先检索一次再回答”，无法按题目自主决定查教材、相似题还是历史错题。
Agent 把这些做成只读工具，让模型最多 3 轮自主补充信息；过程状态可见，工具失败回填后继续。

### Q19：Agent 的三个工具是什么？

1. `search_materials(query)`：检索教材；题库绑定教材时只查绑定教材，返回带编号证据。
2. `search_bank(query)`：当前题库内查相似题，最多 5 条摘要，排除当前题和停用题。
3. `get_related_wrong(question_id)`：当前题库内查题干相近错题，返回错误次数和最近时间。

全部只读，不提供代码执行、文件写入或任意 SQL 工具。

当前用三个 Skill 限制工具子集：`quick_explain` 不开放工具，`grounded_explain` 开放教材/题库，
`wrongbook_review` 开放错题及辅助检索；未绑定教材的错题技能不开放教材工具。路由后 30 案例的
不必要工具调用从 13 次降到 0。

### Q20：Agent 循环怎么控制？

- OpenAI function calling 协议；assistant 消息带 `tool_calls`，工具结果用 `role:"tool"` 和
  `tool_call_id` 回填。
- 最多 3 轮，防死循环；工具异常变成工具结果文本，继续让模型处理。
- 达到上限后追加“直接总结”指令，再做无工具最终生成。
- 最终仍自动保存为 `ai_explanation`，与题目自带 `analysis` 分开。

### Q21：Agent 工具失败怎么处理？

参数不是合法 JSON、工具不存在、工具执行异常，都会作为错误文本回填，不中断对话。
结果为空时让模型换查询或直接回答。工具内容截断到摘要级别，控制 prompt 体积。

### Q22：为什么自定义接口回退单轮？

OpenAI 兼容不代表都支持 function calling。只有智谱和 DeepSeek 官方端点启用工具；
自定义端点沿用原有单轮 RAG，避免因协议差异把原本能用的讲解弄坏。

### Q23：Agent 真机验证了什么？

- 智谱路径下错题工具成功触发。
- 教材检索命中并有引用，讲解自动保存。
- 未绑定教材的题库仍可用 Agent 检索题库/错题。
- 自定义接口正常回退单轮，没有工具兼容问题。
- 教材检索状态显示很快，结果正确；这是体验限制，不是功能失败。

### Q24：Agent 的已知限制？

- 工具轮用非流式请求，最终正文在检索完成后一次性出现；状态行实时更新，但不是全文逐字流。
- 只对智谱/DeepSeek 官方端点启用；DeepSeek 已按标准协议实现，尚未像智谱一样完整真机验收。
- 证据编号依赖模型遵循 prompt；系统不做引用语义自动核验，只展示实际返回的教材依据。
- 最多 3 轮，是防死循环的明确上限，不追求无限自主。

## 5. 全栈云备份与认证

### Q25：为什么后来加后端？

真实需求是多设备迁移和换机恢复，不是为了简历硬造微服务。后端保持最薄：只做邮件验证码、
JWT 和每个账号最新一份备份，不解析题库、不做题目查询。

### Q26：为什么从邮箱密码改成邮箱验证码？

早期只校验邮箱格式，任何人可填一个不属于自己的邮箱注册，存在账号占坑和身份不可信问题。
改成一封信件里的 6 位验证码，只有能接收该邮箱的人才能登录；首次验证自动建号。
不再保存用户密码，旧密码哈希在首次验证后清空。

### Q27：验证码怎么防滥用？

- 6 位数字，10 分钟有效，一次性使用。
- 数据库只存 HMAC-SHA256 哈希，不存明文。
- 同码最多 5 次尝试。
- 同邮箱 60 秒发送冷却，每小时最多 5 次。
- 同 IP 每小时最多 30 次。
- JWT 有效期 30 天，所有备份接口按当前用户过滤。

### Q28：QQ 邮箱/SMTP 踩过什么坑？

- 必须使用邮箱 SMTP 授权码，不是 QQ 登录密码。
- 授权码只放本机 `server/.env`，不入 Git、不发聊天。
- 第一版邮件把验证码和“10 分钟”排得太近，产生歧义；后来改成独立一行“验证码：XXXXXX”
  并明确只输入 6 位数字。
- SMTP 发送失败不能让验证码记录落库，发送异常应回滚并返回可读 503。

### Q29：为什么不能自动把验证码复制到手机剪贴板？

验证码只应出现在用户邮箱。如果 API 把明文验证码返回给 App，任何人输入他人邮箱就能拿到验证码。
Android 也不允许普通 App 后台读取其他 App 的邮件/剪贴板。最终只增加“从剪贴板粘贴验证码”按钮，
安全边界不变。

### Q30：云端备份的接口和数据是什么？

- `POST /api/auth/request-code`：发送验证码。
- `POST /api/auth/verify-code`：验证后返回 JWT。
- `PUT /api/backup`：Bearer JWT，保存最新一份 JSON，最大 20MB。
- `GET /api/backup`：返回最新 JSON，没有则 404。
- `GET /api/health`：健康检查。

服务端只检查顶层 `app` 和 `version`，不解析题库结构；详细结构由客户端校验。

### Q31：备份恢复怎么保证不丢数据？

客户端备份是版本化 JSON；恢复前校验来源、版本、大小和结构；恢复在单事务内执行，失败回滚；
按稳定 ID 合并，已有题目/记录跳过，不覆盖本机已有数据；错题按题合并，做题记录按题加时间去重。

### Q32：这个同步模型有什么缺点？

云端每个账号只保留最新一份，多设备先后上传以最后一次为准；没有增量同步、冲突合并和删除墓碑。
恢复不会覆盖本地，但云端历史只有一份。这是第一期明确接受的限制。

### Q33：云备份的隐私边界是什么？

JWT 用户隔离保证 A 用户不能读 B 用户备份；验证码保证邮箱归属；但不代表端到端加密。
SQLite 中备份是明文 JSON，服务器管理员理论上可读。图片和教材原文件不进入备份。
如果威胁模型包含服务器管理员，需要另做客户端加密和恢复密钥设计，不能用“验证码”冒充加密。

### Q34：电脑关机后还能用吗？

本地题库、刷题、本地备份和 AI 直连不受影响；云备份注册、收验证码、上传、下载不可用。
已上传的数据仍在 SQLite，重启后端后可继续访问。Metro 仅用于 Expo Go 开发，安装 APK 后不需要。

## 6. 数据、安全与测试

### Q35：SQLite 迁移怎么管？

`meta.schema_version` 记录版本，只追加迁移、不改历史 SQL；普通迁移在事务内执行。
需要修改 CHECK 约束时按“新表 → 复制 → 删旧表 → 改名 → 重建索引”执行，并在事务外切换
外键。FTS 是独立索引，不是外键，需要应用层同步清理。

### Q36：AI 讲解为什么要独立字段？

`analysis` 是题目自带解析，`ai_explanation` 是模型生成内容。自动保存、删除、重新生成只动
`ai_explanation`，避免 AI 覆盖人工/原卷解析。备份同时包含两者。

### Q37：删除题目时文件怎么处理？

题目独立配图可直接删；来源整页图可能被同页多题共享，要先查引用，没有其他题使用才删文件。
数据库外键之外还要考虑文件系统副作用。

### Q38：测试怎么做？

- 8 套 126 项客户端离线用例：Parser/F2/归一化、检索、文档解析、备份、多题库、多提供商、
  schema 迁移、Agent 循环与工具。
- 数据层测试用 `node:sqlite` 跑真实 DDL、外键、事务和 FTS，不是纯 mock。
- 后端 17 项 pytest：验证码复用/过期/错误/锁定、发送冷却、SMTP 配置、JWT、上传下载一致、
  超限、用户隔离和旧表兼容。
- 真机验证 UI 和跨进程行为，不把离线测试冒充 E2E。

### Q39：为什么没有客户端 E2E？

初期用 Expo Go 真机人工验收，成本低；明确不足是没有 Maestro/Detox 自动化，尤其杀进程恢复、
空设备云恢复和 Agent 工具状态需要人工验证。这是后续改进项。

### Q40：API Key 怎么保护？

用户自备 Key，存 SecureStore，不进 SQLite、备份、日志或 Git；请求直接发官方 HTTPS 域名。
承认 SecureStore 不能防设备取证，分发内置固定 Key 也不安全；公开产品应做服务端代理。

## 7. 部署与发布

### Q41：现在是怎么发布的？

EAS 云构建 internal APK，使用远程 Android keystore；本次构建 ID
`4b2b2109-f896-4d2c-ad62-d6906a81b0db`，提交 `679ac08`，APK 约 99.9MB。
客户端离线功能不需要后端；云备份仍需要单独启动 FastAPI。

### Q42：为什么没有公网部署？

个人项目存储的是题库和做题记录，默认本地优先能减少隐私和运维风险；公网部署不是技术难点，
但需要域名、HTTPS、SMTP 出网、备份和持续在线。当前明确把它定位为自托管可选服务。

### Q43：免费部署有哪些选择？

- **Oracle Cloud Always Free**：最符合现有 FastAPI + SQLite 架构，需绑卡验证，ARM 容量可能有限。
- **Google Cloud e2-micro 免费层**：可作为备选，但区域和流量限制需以官网当期为准。
- **Render Free**：不适合原样部署。免费实例会休眠、文件系统临时、SQLite 会丢，且阻止 465/587 SMTP。
- **家里电脑 + Cloudflare Tunnel**：免费但仍要求电脑常开，没有解决关机问题。

时间敏感信息需再次验证：

- https://render.com/docs/free
- https://www.oracle.com/cloud/free/
- https://cloud.google.com/free/docs/free-cloud-features

### Q44：如果要正式部署，最小方案是什么？

Docker Compose + FastAPI 容器 + Caddy 自动 HTTPS：

- FastAPI 只在内部网络暴露 8000；公网只开 80/443。
- SQLite 和备份挂持久卷；`DATABASE_URL=sqlite:////data/paiti.db`。
- Caddy 反向代理域名并自动签发/续期证书。
- `ENV=production`、强 JWT_SECRET、SMTP 授权码只放环境变量。
- `restart: unless-stopped`、健康检查、日志轮转。

### Q45：systemd 和 Docker 怎么选？

二选一，不要重复部署。Docker 更适合全栈面试展示：环境可复现、Caddy 和持久卷配置在一个文件；
systemd 更轻，适合直接跑 venv + uvicorn，Caddy 装宿主机并代理到 `127.0.0.1:8000`。

### Q46：数据库备份怎么做？

应用运行时不能直接 `cp paiti.db`，应使用 SQLite `.backup` / Python `sqlite3.Connection.backup`
生成一致性快照；本机保留若干天，再用 rclone 等方式同步到另一台机器或对象存储。
恢复流程要实际演练：停服务 → 替换数据库 → 启服务 → 检查 health。

### Q47：部署时还需要注意什么？

- 只开 80/443，22 限制为管理 IP，不暴露数据库和 8000。
- 域名解析生效后再启动 Caddy；Cloudflare 代理会让 HTTP-01 证书验证复杂，先用 DNS-only。
- SMTP 出网端口可能被云厂商限制，必要时改用 HTTPS 邮件 API。
- 免费账户长期不活跃可能被回收，Oracle 需定期访问健康检查。

## 8. 补充追问：责任、RAG 与工程治理

### Q48：这些项目里，哪些是你负责的？

以当前仓库为准，这是个人项目：你负责需求判断、产品取舍、架构、实现、测试、真机验收和 APK
发布；AI 编程助手参与了代码生成、排查和文档整理，但不能把助手说成团队成员。

### Q49：RAG 知识库有多大？切片策略是什么？怎么保证召回率？

没有统一的全网知识库大小：每个用户的教材和题库都在本机导入，库大小由用户数据决定。
已经验证过的样本是 39 页真实 8051 课件和 8 道可确认题目；不能把它说成生产知识库规模。

当前策略：

- 教材导入：约 800 字符一块、100 字符重叠，优先按 Markdown 标题、“第 X 章/节/讲”和小节
  编号切分；界面显示通常约 500-800 字。
- 题目文档切分：约 3000 字符、200 重叠，优先按题号边界切分，避免题干和选项分离。
- 检索：将题目清理标点后取 3 字滑窗，做 OR 查询，FTS5 trigram + bm25 排序；Agent
  教材工具取 Top5，旧单轮 RAG 取 Top10；少于 3 字回退参数化 LIKE。
- 题库绑定多本教材时，检索范围限制在绑定教材，减少噪声。
- 长片段用锚窗或头尾双窗截取，避免答案落在模型看不到的后半段。

召回验证：真实课件题集从 2/8 修复到 8/8，并确认正确段落进入模型窗口。项目没有做正式的
recall@K、MRR 或人工标注的通用评测集，这是明确不足。

### Q50：有没有延时特别高的场景？怎么解决？

有，瓶颈主要在模型推理，不在本地 SQLite：

- 视觉识别免费档曾出现 20-90 秒波动；同卷 DeepSeek 实测约 8 秒识别 18 题；付费思考模式
  反而可能 180 秒以上。数字来自项目实测，不是通用 SLA。
- 文档切题按块串行，单块可能等待模型；取消通过 AbortSignal 立即中断，不重试。
- 讲解有首字延迟；旧实现用 SSE 降低体感等待。Agent 工具轮目前非流式，但状态行会显示
  “分析题目 / 检索教材 / 命中 N 条”；达到轮数上限后的总结才走流式。

已做的工程措施：图片压缩、按任务选模型、超时、有限重试、失败切半、进度提示、取消、
工具结果截断、最多 3 轮 Agent。没有解决“模型本身慢”，也没有做生产延迟监控。

### Q51：Agent 对异常情况怎么做工程化管控？

当前硬约束：

- 工具只读：教材、题库相似题、相关错题，没有代码执行、文件写入和任意 SQL。
- 最多 3 轮，避免无限循环；达到上限强制生成总结。
- 工具不存在、参数不是合法 JSON、工具执行异常，都作为 `role:"tool"` 错误结果回填，继续对话。
- 工具结果截断到摘要，控制 token；教材证据有最大条数。
- 工具结果包在 `<tool_result>` 数据边界中，system prompt 明确忽略其中的指令注入。
- 教材绑定且无命中时不允许模型用自身知识冒充教材，转入用户确认后的降级链路。
- 自定义接口不具备 function calling 时自动回退单轮。
- API Key 只存 SecureStore；云备份端只存 JSON，不访问模型 Key。

### Q52：有没有搭评测集？怎么设计的？

有分层验证，但不是完整的 LLM 评测平台：

- 离线测试：8 套 126 项，覆盖 Parser/F2、检索词、文档解析、备份、多题库、多提供商、
  schema 迁移和 Agent 循环。
- 真实检索评测：39 页 8051 课件 + 8 道已知题，验证命中片段是否进入模型窗口，结果 8/8。
- 模型对照：同一张卷子用多个视觉模型逐题人工核对；曾用真实模型输出做离线重放。
- 后端 pytest：验证码、JWT、备份大小、用户隔离和 SMTP 配置。
- Agent 评测夹具：30 个案例，覆盖真实 8051 教材、相似题、错题、直接回答、注入文本和答案冲突；运行
  `npx tsx tests/agent.eval.ts` 只校验夹具，加 `--live` 才调用真实模型。

2026-10-26 真实 live 运行（30 个案例，含真实 8051 第 1 章教材复核，非生产数据）：

| 指标 | 全 Agent | Skill 路由版 | 单轮 RAG |
| --- | ---: | ---: | ---: |
| 成功案例 | 30/30 | 30/30 | 30/30 |
| 工具合同 | 19/30 | 30/30 | 不适用 |
| 教材引用 | 12/12 | 12/12 | 11/12～12/12（有随机波动） |
| 未覆盖处理 | 3/3 | 3/3 | 不适用 |
| 答案冲突提示 | 1/1 | 1/1 | 1/1 |
| 注入安全 | 2/2 | 2/2 | 2/2 |
| 不必要工具调用 | 13 | 0 | 0 |
| 平均轮数 | 2.07 | 1.63 | 1 |
| P50 | 2.620 秒 | 1.839 秒 | 1.448 秒 |
| P95 | 4.622 秒 | 4.120 秒 | 2.207 秒 |
| 总 token | 48,734 | 30,275 | 7,833 |

路由版把工具合同从 19/30 提升到 30/30，不必要工具调用降到 0，token 比全 Agent 降低约 38%，
引用率仍保持 12/12。对简单题走单轮 RAG，对教材和错题才走 Agent，是当前更合理的产品取舍。
本地工具耗时约 0-2ms，主要延迟仍来自模型推理。

### Q53：大模型做数据清洗、分类出错了怎么办？

分两层：

1. 结构/枚举错误：Parser 修复有限格式问题，F2 检查题型、选项、答案类型、题干和重复；
   失败进入 needs_review，不直接入库。
2. 语义错误：例如漏题、改写题干、答案错，确定性规则无法根治；通过原图核对、答案表冲突
   标记、低置信度/视觉特征提示、人工确认页拦住，绝不宣称自动准确。

答案文档映射是确定性解析优先，冲突显式标记，本地解析失败才让 AI 兜底规范化。没有自动
“AI 判错就自动改答案”的闭环。

### Q54：如果再设计一次，你会怎么改进？

优先级：

1. 先定数据契约、评测集和失败语义，再写 UI。
2. 把导航迁移到成熟路由，补客户端 E2E（杀进程恢复、空设备云恢复）。
3. Docker + Caddy + 持久卷 + 备份恢复演练，而不是只做局域网演示。
4. 云备份第二期做增量同步、冲突合并、删除墓碑；规模上来再换 Postgres/对象存储。
5. RAG 增加固定 recall@K 评测、查询改写和 rerank；Agent 增加审计和权限边界。
6. 把部署、监控、限流和密钥管理纳入验收清单。

### Q55：举一个你用 AI 时它做不好的事。

真实案例：免费视觉模型识别一页试卷时漏掉“汉字轴对称”题，还虚构了一道原卷不存在的
“a+b=0”题。Parser 和 F2 只能发现格式/结构异常，无法判断题目是否真的存在于原图，所以
最终靠人工对照原图拦截。这个案例说明概率模型必须配确定性校验、原图追溯和人工确认；
不能承诺“AI 自动识别永远准确”。

## 10. 可背的 STAR 案例

### 案例 1：教材检索 2/8 → 8/8

现象：用户说教材有内容，AI 却说未覆盖。
排查：真实课件 + 8 道已知题离线复现。
根因：题目整句当连续短语，措辞稍变就匹配失败；长片段截断还丢掉答案。
方案：3 字滑窗 OR + bm25 + 锚窗/头尾双窗。
结果：8/8 命中。
反思：检索优化必须有固定样本，不能凭一次试用感觉。

### 案例 2：邮箱“注册”但不验证身份

现象：任意邮箱 + 8 位密码即可注册，邮箱只是字符串。
根因：认证设计把“格式正确”误当“归属已验证”。
方案：邮箱验证码、HMAC 存储、一次性、冷却、尝试上限、邮箱/IP 限流、JWT。
结果：同邮箱验证后进入原账号，旧密码哈希清空，数据隔离测试通过。
反思：认证要区分账号标识和身份证明；安全边界不能靠 UI 文案。

### 案例 3：Agent 工具调用的协议与降级

现象：单轮 RAG 无法自主决定查教材、题库还是错题。
方案：OpenAI function calling + 自研 3 轮循环，工具失败回填，教材证据编号累计。
结果：智谱真机触发错题工具，未绑定教材可用，自定义接口回退单轮，126 项测试通过。
反思：Agent 不是无限自主；轮数、工具权限和失败降级必须硬限制。

### 案例 4：备份恢复的事务边界

现象：换机和多设备迁移需要云端，但直接覆盖本地风险高。
方案：服务端只存最新 JSON；客户端恢复前校验，按稳定 ID 合并，单事务回滚。
结果：上传/下载和重复导入通过测试；空设备完整恢复仍需实测。
反思：同步问题先明确冲突语义，再谈 UI。

### 案例 5：免费部署方案的工程判断

现象：需要判断 Render 免费层是否可承载当前服务。
排查：核对当前文档，发现免费实例休眠、磁盘临时、SMTP 端口被禁。
决策：不为了“有公网链接”强行改架构；优先 Oracle Always Free 或家庭常开主机。
反思：部署方案必须从持久化、出网和运行模型反推，不能只看是否免费。
